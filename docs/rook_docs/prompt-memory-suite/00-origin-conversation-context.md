# Origin Conversation Context

## Initial user problem

The feature request started from a concrete user quote about reusing prompts in RookVision:

> "Most frequent, and recent… like a recently opened file list"

The original framing was intentionally UX-led:

- The immediate surface is RookVision prompt reuse for imagery generation.
- The chat panel may share the same capability, but should not obscure the Vision-first need.
- The design should be grounded in the current codebase rather than treated as greenfield.

## Initial interpretation

The quote maps to three user jobs:

1. Recover: "What did I just use?"
2. Reuse: "Let me run or edit that exact prompt again."
3. Refine: "Show me commonly used prompts so I can evolve them."

That yields two basic ranked lists:

- Recent: time-based, newest first.
- Frequent: use-count or weighted frequency-based.

The first UX analogy is an MRU list, like recently opened files in editors.

## Option ladder from the brainstorming session

### Option A: Per-surface local lists

Vision keeps its own recent/frequent list. Chat keeps its own recent/frequent list. There is no cross-pollination.

Advantages:

- Fastest to ship.
- Low schema and boundary risk.
- Easy to validate demand.

Costs:

- The user's mental model may fragment if prompts feel trapped in one surface.
- It does not establish a reusable platform capability.

### Option B: Unified prompt memory with source tags

One shared prompt memory store captures entries from multiple surfaces and tags them by source, such as `vision_generate`, `vision_enhance`, `vision_video`, `chat`, or an agent operation.

Advantages:

- Matches a "my prompts in Rook" mental model.
- Supports filtering by surface while allowing global reuse.
- Creates a foundation for pinning, templates, provenance, and later agent use.

Costs:

- Requires dedupe, ranking, privacy, and scope decisions.
- Crosses more architecture boundaries than a Vision-only MRU list.

The preliminary recommendation was Option B as the product foundation.

### Option C: Command palette style prompt launcher

Option C was framed as Option B's professional interaction shell, not a replacement for Option B.

Capabilities discussed:

- Searchable dropdown or palette in prompt inputs.
- Weighted results from recency, frequency, fuzzy text match, context, provider/model affinity, and pins.
- Keyboard-first interaction: open palette, type a few characters, arrow/enter to choose.
- Per-prompt actions: Insert, Insert + Run, Pin/Unpin, Duplicate as Variant, open lineage/history, copy to another surface.
- Context filters: Vision, Chat, Project, Provider, Agent, Shared.
- Lightweight ranking explanations such as "Used 8 times this week", "Last used in Vision yesterday", or "Pinned".

The UX quality bar proposed for Option C:

- Perceived open-to-result latency under 100 ms.
- No modal friction for core actions.
- Insert into the input by default; always allow edit-before-run.
- Consistent behavior across Vision and chat.
- Predictable ranking with lightweight explanations.

The preliminary roadmap was:

1. C1: searchable dropdown/palette, unified ranked results, Insert/Insert + Run, keyboard navigation.
2. C2: pinned prompts, tags, variants, context filters.
3. C3: lineage graph/timeline, outcome-aware ranking, optional shared/team libraries.

## Knowledge graph expansion

The knowledge graph entered after the user explicitly asked to factor in:

- the relationship to the knowledge graph,
- foundational tool use by agents,
- local and cloud agents,
- agents as first-class citizens alongside human users.

This changed the abstraction from "prompt history" to "shared cognitive substrate." In that framing, prompts are not just strings; they are reusable intent artifacts with graph relationships.

Conceptual node types discussed:

- Prompt
- PromptVariant
- Session
- Artifact
- Agent
- HumanUser
- Project/Document
- ToolOp
- Style/Tag

Conceptual edge types discussed:

- `DERIVED_FROM`: variant lineage.
- `USED_IN`: session or operation context.
- `PRODUCED`: prompt to generated artifact.
- `SELECTED`, `APPROVED`, `DOWNLOADED`: outcome signals.
- `AUTHORED_BY`: human or agent provenance.
- `EXECUTED_BY`: runtime or agent executor.
- `SCOPED_TO`: project, document, or workspace.
- `SIMILAR_TO`: later semantic proximity.

Human-facing unlocks:

- "Show prompts that produced approved facade renders in this project."
- "Reuse the most successful dusk-lighting variants."
- "Find prompt branches generated by agent X that I later edited."

Agent-facing unlocks:

- Query prompt memory before acting.
- Reuse high-performing variants.
- Write new variants without overwriting human prompts.
- Explain choices with graph evidence.
- Coordinate local and cloud agent workflows through shared lineage.

Governance requirements identified:

- Mark authorship unambiguously.
- Preserve immutable lineage.
- Allow human override and pinning.
- Keep an audit trail.
- Respect local-only, project, shared, and cloud scopes.
- Prevent agent-generated memory from becoming noisy.

## Important review note

The graph-backed human/agent substrate is a valid strategic extension, but it is not the same as the initial user request. The docs should preserve both:

- The immediate MRU/frequent UX problem.
- The larger Prompt Memory Graph architecture.

The implementation plan should not treat the full graph substrate as required for the first user-visible slice unless we explicitly choose that scope.
