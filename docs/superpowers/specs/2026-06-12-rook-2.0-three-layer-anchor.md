# PART I — THE VISION (THE ANCHOR)

## 1. Who this is for, and who is building it

Rook is a plugin that brings AI-driven design assistance into Rhino 3D, built **by a practicing architect, for practicing architects.** Its author is a building architect who programs — not a software architect by trade. That origin is not a caveat; it is a design force. The system's most important ideas come from how buildings actually get coordinated, not from how software is conventionally layered.

In the author's words:

> *"I am an Architect of buildings who knows how to program computers, and I've been writing this plugin to help my fellow colleagues. The McNeel devs might have a better sense of [the software architecture], but they will never take their RhinoMCP plugin to the places that I want to go. I'm trying to leverage their intelligence and effort, without losing Rook's core."*

That sentence is the whole strategy in miniature, and the rest of this document is its formalization.

## 2. The thesis (Rook's center of gravity)

**Rook's durable bet is local-first intelligence + a persistent knowledge graph + coordinated multi-agent behavior, with Rhino as one attached capability provider among several.**

This is deliberately *not* "a better Rhino MCP server." Generic Rhino control is a lane the platform vendor (McNeel) will own. Rook's reason to exist is the reasoning layer on top: agents that know *what* to do in a Rhino model, *why*, and *how to recover* — carried by accumulated, project-spanning design knowledge rather than by raw model horsepower.

## 3. The relationship to McNeel (leverage **and** diverge)

McNeel's release of RhinoMCP is treated here as a **gift, not a threat.** It is a clean, well-engineered, vendor-blessed solution to a layer Rook genuinely lacks (multi-instance access, lifecycle, crash recovery, connector packaging). The correct response is neither to ignore it nor to be absorbed by it, but to **ride it where it is strong and diverge where Rook is unique:**

- **Leverage them** for the access/transport/lifecycle ergonomics — the boring, hard, must-stay-current plumbing.
- **Diverge from them** in the two places they will structurally never go: (a) a **local-first, knowledge-subsidized, multi-agent coordinator**, and (b) a **native in-Rhino floor** that reaches capabilities a C#/RhinoCommon architecture cannot.

The McNeel developers are excited about Rook precisely because Rook explores the territory their official architecture cannot prioritize. This document is written to keep that collaboration honest: contribute back at the shared layer, diverge cleanly above and below it.

## 4. The two-tier economic gradient (from the north-star)

The orchestration vision is a **two-tier coordinator with an explicit cost/intelligence gradient** (developed in full in `2026-06-03-rook-north-star-topology.md`):

- **Top tier — one expensive brain (cloud-grade model weights, running locally).** Owns macro work: decomposing a large design workflow across many Rhino files, disciplines, and options; conflict resolution; deciding *"what does done look like."*
- **Bottom tier — many cheap brains (local, ideally ~$0).** Each Rhino file is worked by its own swarm of cheap/local-model agents doing the in-file micro work.

**The knowledge graph is the subsidy that makes the cheap tier viable.** A weak local model does not need world-knowledge if intent-routing, typed routes, learned conventions, and structured diagnostics carry the competence. This is the load-bearing empirical bet of the whole vision (see Part V, Open Question 3).

## 5. Fan-in: the payoff, and the building-architecture metaphor

The vision's true payoff is not fanning work *out* across files — it is **recomposing the outputs back into a master deliverable.** Each file's swarm produces a piece; the pieces are reconciled into a master/anchor document through Rhino's native composition mechanisms — worksessions, linked models, references, blocks, imports.

This is not borrowed software thinking. **It is how building architects already work:** a coordinated master model assembled from consultants' and disciplines' referenced files, each authored independently, composed and refreshed against a shared anchor. The vision applies that lived practice to AI-driven design. The author's domain expertise is the source of the system's most distinctive idea, and the "fan-in is the under-built half" insight is the architectural instinct asserting itself correctly.

# PART II — THE COHERENT ARCHITECTURE (THE THREE-LAYER SPINE)

The project has oscillated — "rubberbanded" — between C++ and C# for years. The diagnosis (Part III) is that **the oscillation came from treating the bridge language as *the architecture.*** The cure is to stop deciding at the bridge layer and instead fix three horizontal layers, each with a single owner, a single home language, and a clear relationship to McNeel. Once each language has exactly one home, **there is nothing left to swing on.**

```
┌──────────────────────────────────────────────────────────────────────┐
│ LAYER 3 — PUBLIC ACCESS & LIFECYCLE                  ▸ LEVERAGE McNEEL │
│   Router · multi-instance slots/sessions · auto-launch · crash         │
│   recovery · MCPB connector packaging.                                 │
│   Runs OUTSIDE Rhino. Rhino-agnostic. Cross-platform-friendly.         │
│   This is what McNeel built well and Rook lacks. "Ride" them here.     │
├──────────────────────────────────────────────────────────────────────┤
│ LAYER 2 — ROOK COORDINATOR BRAIN                          ▸ ROOK'S CORE │
│   Python: persistent knowledge graph · intent runtime · local-model    │
│   swarms (Planner/Worker/Specialist) · fan-out → fan-in recomposition  │
│   · Chirp.  This is the product. Where McNeel will NEVER go.           │
│   Never leaves Python (the ML/KG ecosystem lives here).                │
├──────────────────────────────────────────────────────────────────────┤
│ LAYER 1 — IN-RHINO SURFACE                               ▸ ROOK'S FLOOR │
│   RookNative (C++): the sole in-Rhino HTTP / capability / control /     │
│   discovery surface (project invariant) + the genuinely-native         │
│   capabilities (real-time display, media encoding, native analysis).   │
│   Windows-bound today; the only layer that is.                         │
└──────────────────────────────────────────────────────────────────────┘
```

### The three layers, defined

| | **Layer 1 — In-Rhino Floor** | **Layer 2 — Coordinator Brain** | **Layer 3 — Public Access** |
|---|---|---|---|
| **Purpose** | Execute real work inside Rhino; expose native-only capability | Decide what to do, learn, coordinate agents, recompose deliverables | Address/launch/recover Rhino instances; package for clients |
| **Owner / language** | RookNative — **C++** | Rook runtime — **Python** | Router/connector — **C# (or Python; see Open Q1)** |
| **Runs** | Inside the Rhino process | On the workstation (local runtime) | On the workstation, outside Rhino |
| **McNeel relationship** | **Diverge** — they can't follow into native | **Diverge** — they will never build this | **Leverage** — adopt their proven patterns; contribute upstream |
| **Settled?** | Yes — invariant | Yes — center of gravity | **Spine settled; home language is the one open question** |

**A Layer-2 refinement (added in revision).** Layer 2 carries the same leverage/moat split as the other floors — an *agent-runtime substrate* (a concrete candidate: NousResearch's **Hermes**) and the *domain intelligence* (the knowledge graph + intent runtime + Chirp, the irreducible moat). The runtime belongs at the **bottom (worker) tier**, with Rook owning the top coordinator and the product identity; the adoption topology is **Open Question 7**.

### Why exactly three, and why this dissolves the rubberbanding

The instability was never "C++ vs C#." It was that the bridge — the seam between Python and Rhino — kept being treated as the load-bearing architectural decision, so there was always a credible case to swing the other way. Layering removes the seat the oscillation sat in:

- **C# has one home: Layer 3** (out-of-Rhino access ergonomics).
- **Python has one home: Layer 2** (the brain, where the KG and ML live).
- **C++ has one home: Layer 1** (the in-Rhino floor and native-only capability).

**The architecture *is* the layering, not any one language.** A future idea no longer asks "should this be C++ or C#?" — it asks "which floor does this belong on?", which is answerable and stable.

# PART III — THE REASONING (CODE-GROUNDED EVIDENCE)

This part embeds the investigation that justifies the spine. It is the "refinable" half: check it, correct it, push on it.

## Layer 1 — the in-Rhino floor: what RookNative actually is

A handler-by-handler read of `src/RookNative/` shows RookNative is **roughly one-third genuine native capability and two-thirds commodity bridge glue.**

- **Genuinely native (Layer-1-worthy):** real-time display overlay (`SceneGraph/SceneGraphConduit.cpp`, a `CRhinoDisplayConduit` subclass drawing into Rhino's render loop), video/media encoding (`Handlers/DirectorHandler.cpp`, Windows Media Foundation `IMFSinkWriter` → H.264), and performant native geometry analysis (`Handlers/AnalysisHandler.cpp`, `MeasureHandler`).
- **Commodity (could live in any well-built plugin):** layers, blocks, objects, materials CRUD, and — notably — the **Grasshopper and Vision handlers, which are pure P/Invoke trampolines** marshaling JSON to a managed C# companion (`Handlers/GrasshopperProxyHandler.cpp`), with zero native logic.

**The honest moat is small — roughly 5% is truly C#-impossible.** This is the most important correction in this document, and it cuts *against* an earlier, more flattering framing:

- The real-time display conduit is **not** C++-only. It **ran in C# first** (`SceneGraphConduit.cs` in the archive), and RhinoCommon exposes `Rhino.Display.DisplayConduit`. It moved to C++ for *explicit thread control*, not a missing API.
- Analysis, measure, display modes, offset/split/SubD/mesh, and gumball all have RhinoCommon equivalents.
- The one genuinely irreducible item is **Windows Media Foundation video encoding** (`DirectorHandler`), plus possibly Win32 input hooks for a persistent gumball.

> **Do not over-read the "5%" (post-review correction).** That figure is the *narrowest* reading — "no managed API exists at all." It does **not** count the cases where C++ gives a *material performance / determinism advantage even though a managed API exists*: real-time display drawn at frame rate without GC hitching (the scenegraph conduit), bulk / large-data geometry that would otherwise marshal across the boundary, block merging/analysis hot loops, low-latency interaction, and explicit threading control. **That bucket is larger and unmeasured** — these are *code classifications, not benchmarks.* So the operative rule is **not** a percentage: **the line between "native core — keep in C++" and "shed to managed" must be drawn by profiling the real hot paths.** Firm product constraint: **we keep the C++ core where it earns its keep; we do not make the plugin worse to reach a new platform** (see Open Q8).

### Why C++ at all? (The Chesterton's-fence investigation)

The project switched from a C# bridge to a C++ native plugin in late February 2026. The archive (`Rook-private-archive`) records *why*, and it matters because Layer 3 reintroduces C# — we must not walk back into the original fire:

1. **The UI-thread trap (fundamental).** The old C# bridge (`RookServer.cs`, an in-process RhinoCommon plugin with an embedded HTTP server) did expensive scene-graph work on Rhino's single UI thread, blocking interactivity. The native-plugin commit states it plainly: *"Replaces C#'s accidental UI thread serialization with explicit thread dispatch via CMainThreadDispatcher."* The win was **explicit, controlled main-thread marshaling — not "C++ is faster."**
2. **The Grasshopper second-runtime dead end (fundamental).** A spike to drive Grasshopper from C++ via `hostfxr` *"created a second .NET runtime that could not see the live Grasshopper.dll state."* Grasshopper can only be driven from inside Rhino's already-loaded managed runtime. This is why the P/Invoke callback trampoline exists — it is a scar, not a design preference.

**The decisive implication for Layer 3:** the pain came from a *badly-architected in-house C# bridge*, not from C# itself. McNeel's RhinoMCP is the *well-architected* C# bridge — Kestrel on worker threads, explicit UI-thread marshaling, running inside Rhino's real managed runtime (so it can drive Grasshopper directly). Adopting C# at Layer 3 (outside Rhino) does not reopen the wound, provided heavy compute stays off the UI thread — which, in this architecture, it does, because compute lives in Layer 2.

### The Layer-1 invariant

From the assessment, preserved here: **RookNative remains the sole *in-Rhino* Rook HTTP / capability / control / discovery surface.** Layer 3 may become the public MCP surface, but nothing displaces RookNative *inside* the Rhino process. (Part V, Open Q6 notes the one real wiring cost this implies.)

## Layer 2 — the coordinator brain: already clean, already the moat

Three findings establish that Layer 2 is both the real differentiator and structurally ready to be the stable center:

1. **Rook's intelligence is already transport-agnostic.** `knowledge.py` (the knowledge graph), `contextual_mab.py` (a Thompson-sampling contextual bandit), and the DSPy consolidation modules import **no transport details** — no bridge, server, socket, or port. `SmartExecutor` already takes its Rhino-caller by **dependency injection**. The ~405 MCP tools are defined as **pure data schemas**, separable from their execution. Only two modules touch the bridge directly. The brain can sit on top of a different floor without being rewritten (estimated ~30% refactor, concentrated in the tool-execution adapter — not a rewrite).

2. **Orchestration already lives *inside* the Python runtime, and agents bypass MCP.** Per `AGENT_ARCHITECTURE.md` / `CURRENT_ARCHITECTURE.md`: *"Agents never use MCP — they call the native HTTP bridge directly."* This is decisive for the spine. It means there are **two distinct boundaries** — an outer one (client ↔ brain) and an inner one (brain ↔ Rhino) — and the C++/C# question belongs *only* to the inner/floor boundary. Orchestration doesn't care which floor executes a call; it calls a dependency-injected function. This is why "the brain orchestrates; substrates serve underneath" is not a preference but a description of how Rook already works.

3. **Local-model coordination is ~40% built, with the seams already in place.** `model_profiles.py` ships `cloud / hybrid / local / lmstudio / finetuned` profiles with per-role models (planner / worker / **specialist** / guardian / dspy), all routed through **LiteLLM** (`api_base` swappable to Ollama / LM Studio), activated by env var or profile file. Today's orchestration is a single-powerful-model fan-out (Opus Planner → parallel Sonnet Workers, with Guardian + Conductor monitors). The net-new work for "sparse local models coordinating" — inter-agent result passing, learned model-routing, specialist dispatch, escalation — is estimated as a **2–3 week extension, not a re-architecture.** The `specialist` role already exists in the data model awaiting a dispatcher.

**Conclusion:** Layer 2 stays Python permanently. The ML/KG ecosystem (DSPy, bandits, local-model tooling) is Python-native; moving it to C# would fight the north star and gain nothing.

## Layer 3 — public access: McNeel is the missing layer, and it doesn't collide with the floor

The assessment already established this from a source read of `mcneel/RhinoMCP`:

- **Same broad substrate, different implementation.** Both McNeel and Rook use an in-Rhino localhost HTTP listener plus a discovery/announcement record. McNeel's advantage is entirely a **separate stdio MCP router process** that owns slot targeting, auto-launch, crash recovery, and client ergonomics — *"capabilities Rook's Python MCP runtime does not yet have."*
- **The router is Rhino-agnostic.** Per the assessment, McNeel's router has *"zero Rhino dependencies."* This is the coherence check that makes the whole spine safe: **adopting C# at Layer 3 cannot violate the Layer-1 invariant, because the router runs *outside* Rhino.** Layer 1 (C++, in-Rhino) and Layer 3 (C#, out-of-Rhino) sit on different floors and never collide.
- **Proven patterns to adopt** (verified in `RhinoMCP/rhino/router/SlotStore.cs`): SQLite slot store with `BEGIN IMMEDIATE` + WAL + "the row is the lock"; *persist intent, probe truth* for liveness; the `adopted` flag distinguishing owned (killable) from adopted (never-killed) sessions; MCPB connector packaging as the cloud brain's entry point.

The north-star's two operating modes — **Workbench** (owned, disposable, may reap+respawn) and **Attached** (adopted, never killed = the human's master document) — are the Layer-3 lifecycle policy, and they map directly onto Rook's existing earned-autonomy levels.

# PART IV — INVARIANTS (immovable)

Carried forward from the assessment and north-star, plus the layering this document fixes:

1. **Three layers, fixed homes.** Layer 1 = RookNative/C++ in-Rhino; Layer 2 = Python coordinator brain; Layer 3 = router/connector access. The architecture is the layering, not the language of any one layer.
2. **RookNative remains the sole *in-Rhino* surface.** A Rook router/connector may become the public LLM/MCP surface; nothing displaces RookNative inside the Rhino process.
3. **The brain stays Python.** The KG, intent runtime, bandits, DSPy, and local-model orchestration never move to C#.
4. **Center of gravity is local-first + KG + coordinated agents**, with Rhino as one capability provider. Rook does not become "another Rhino MCP server."
5. **Fewer, intent-shaped tools for the model surface.** The ~300 typed routes remain implementation substrate beneath an intent/KG-shaped surface; this applies *doubly* to the cheap local tier.
6. **Session ≠ Document ≠ Work Unit; Merge Contract is a dependency-DAG edge** (north-star §5). Never conflate a live execution context with the durable artifact it produces.
7. **Coordinator registries point *down* at sessions; sessions never back-reference work units** (disposability invariant).
8. **Single-workstation bound.** "Cloud" means model weights only; transport stays local (stdio / MCPB / loopback). Multi-machine distribution is a separate XL track.
9. **Compute lifecycle ≠ artifact lifecycle.** Killing a Workbench session must never discard the `.3dm` it produced; the Save membrane is the fan-out → fan-in boundary and the most fragile seam.

# PART V — WHAT IS SETTLED vs. OPEN FOR REVIEW

### Settled (the anchor)

- The vision (Part I) and the three-layer spine (Part II).
- The invariants (Part IV).
- Layer 1 stays C++/in-Rhino and shrinks toward its genuine native core. Layer 2 stays Python and is the product. Layer 3 leverages McNeel's patterns.

### Open Question 1 — **Where exactly does Layer 3 live?** (the lead open question)

Two candidate homes, and the project's own two documents lean different ways:

- **(A) Extend Rook's existing Python router** (`server.py` + `bridge.py`), adopting McNeel's *patterns* (SlotStore schema, adopt/reap, crash envelopes) but reimplementing in Python. *The 2026-06-02 assessment recommended this* — "grown inside Rook's existing Python runtime, not ported from McNeel's C#" — to keep the coordinator's home language and de-risk viability.
- **(B) Adopt McNeel's C# router on the fork** (`github.com/bringfire/Rook-2`), staying upstream-mergeable. *The author's "rebase on the fork" framing points here.*

**The consideration that should decide it: cross-platform.** McNeel's C# router gets **Mac/cross-platform essentially free**; Rook's Mac story is currently XL-blocked *by the C++ native plugin*. If Layer 3 is C# (B), then **only Layer 1 remains Windows-bound** — a materially better cross-platform posture. Against (B): McNeel's router is wired to *their* in-Rhino C# plugin via a source generator, so pointing it at RookNative is a real (bounded) integration cost (see Open Q6). This question is **explicitly deferred to the implementation plan** and is a prime topic for McNeel-developer input.

### Open Question 2 — **In-place evolution (P1–P7) vs. the parallel "rebase" track**

The north-star roadmap (P1–P7) is *in-place* evolution of the current Python runtime. The author's "Rook 2.0" framing proposes a **parallel development track** that rebases Rook onto the McNeel fork to shed organic-growth legacy. These are two change-management strategies for the *same* target architecture. They are not mutually exclusive (in-place hardening can ship while a clean track re-homes Layer 3), but the relationship must be decided so effort isn't split blindly. See Part VII.

### Open Question 3 — **The empirical bet: does KG-subsidy make cheap local models competent?**

The economic gradient rests on *"cheap/local model + KG subsidy ≈ competent-enough in-file."* There is now **partial prior evidence** from the sibling **Engram** project (Unreal-Blueprint domain; ~500 runs across Claude Haiku, Qwen3:14b, Mistral-Nemo-12B), and it *refines* the bet rather than confirming it:

- **Strong model doesn't need the KG (B≈A): confirmed.** Haiku = 100% with and without knowledge injection.
- **"KG transforms cheap models" (C≫D): *not* cleanly supported.** The local models were *already* largely competent without the KG (Qwen3:14b: 90% expert / 100% hard, no injection). The KG gave a **modest, conditional** lift (≈ +2.5–5%), and only when context was sufficient.
- **The real bottleneck was *context economy*, not model intelligence.** Knowledge injection actively *hurt* (≈ −10%) when it overflowed a small context window — which *validates* Rook's "fewer, intent-shaped tools" principle as the actual lever.
- **Finetuning-as-shortcut backfired.** A finetuned local worker *reported* 100% and actually scored **12.5%** (empty responses, asset-path hallucination) — a direct caution for the *finetuned*-models north star: validate base-model competence first.
- **Caveat:** Engram's knowledge store was later found polluted (209K phantom observations); the numbers carry an asterisk.

**What remains genuinely unproven for Rook.** Engram tested a domain (Unreal Blueprints) likely *well-represented* in model pretraining, so base models were already competent and the KG had little to add. **Rhino's parametric/Grasshopper domain is far more niche** — the local base-competence floor is likely lower, which is exactly where a KG subsidy would matter *more*. So the Rhino-domain probe is the real test, and it must be run with Engram's confounders controlled: **sufficient context, a clean knowledge store, base-model-before-finetuning, and measuring the with/without delta *and its context cost.*** The Hermes-based probe (Open Q7) is the apparatus, and it is the **lowest-regret first move** — it commits to nothing structural while answering the one question every later phase depends on.

### Open Question 4 — **Chirp's home.** Chirp (LLM-embedded Grasshopper components) is a proto-multi-agent mechanism at the component level, currently a Python sidecar. It is Layer 2 in spirit but touches Grasshopper (managed runtime). Its precise placement under the new layering needs a deliberate decision.

### Open Question 5 — **The UI surface.** Rook's WebView panels (chat, vision gallery, knowledge graph) are a C# in-Rhino surface today. Under the spine they are a thin Layer-1-adjacent C# UI plugin; whether they fold into RookNative, ride alongside, or move is open.

### Open Question 6 — **Router → RookNative wiring cost.** If Layer 3 adopts McNeel's C# router (Open Q1-B), it must be re-pointed from McNeel's in-Rhino plugin to RookNative's HTTP surface, and its source-generated tool proxies adapted. Bounded and solvable, but real; it must be scoped in the plan.

### Open Question 7 — **Hermes as the Layer-2 runtime: adoption topology**

NousResearch's **Hermes** (MIT) is a mature agent runtime — agent loop, native subagent delegation, first-class local-model support, kanban worker farm, MCP client+server, trajectory capture — i.e., the agent-runtime *plumbing* Rook hand-built (`base_agent.py`, planner/spawn/conductor, `model_profiles`). It is a candidate Layer-2 *runtime substrate*, with Rook's KG + intent + Chirp as the *domain-intelligence payload* (the moat). Hermes has **no knowledge graph**, so the two compose rather than collide.

**The topology question — where Hermes sits relative to Rook:**
- **(A) Hermes as host** — Rook becomes plugins/skills + an MCP-reached RookNative floor, possibly a Rook-branded Hermes *distribution*. Max leverage (inherits Hermes's whole product surface), but Rook's identity becomes a vertical on Hermes, and Rook's in-Rhino UI + bespoke multi-file coordinator do not fit cleanly as "a plugin."
- **(B) Rook as host, Hermes embedded** — Rook keeps its identity, UI, and north-star coordinator, using Hermes's loop/delegation as an engine. Fights Hermes's app-not-library grain; more coupling to track.
- **(C) Peer processes via MCP/ACP** — the original "harness" framing; loosest coupling, least leverage of the engine.

**Recommended reading (resolves the inside/outside ambiguity via the two-tier north-star):** place Hermes at the tier it is strongest — the **bottom**. Hermes's delegation + local-model running + kanban + trajectory capture are all bottom-tier worker tools. So **Rook owns the top tier** (macro coordinator, fan-in, KG, UI, product identity = the host) and **Hermes powers the bottom tier** (the per-file cheap-local worker swarm). "Hermes inside Rook, as the bottom-tier engine" — *not* Hermes as the outer host. The remaining sub-decision (implementation mechanic): embed Hermes's `AIAgent` as a library vs. drive a Hermes swarm as a subprocess — deferred to the plan.

**Lowest-regret first move:** use Hermes as the rig for the Open-Q3 probe (cheap-local workers + KG ablation). That tests the empirical bet *and* is the first real trial of Hermes-as-bottom-tier-engine — committing to nothing structural.

### Open Question 8 — **Cross-platform / Mac (the honest path)**

**The product constraint is firm:** we keep the C++ core at full strength and **do not degrade the plugin** to reach a new platform. Given that, the conclusions are blunt:

- **Hermes does *not* solve Mac.** Hermes is Layer 2 (the brain), which is already cross-platform. The Mac problem lives **entirely in Layer 1** (the C++ floor). No orchestration trick relocates native execution *onto* a Mac — it can only relocate it to *another Windows machine*, which is a Windows-in-the-loop **workaround (VM / remote / cloud Windows), explicitly rejected** as "the architecture."
- **The only non-degrading path to native Mac is to port RookNative (Layer 1) to macOS.** Full stop. The layering does one good thing here: it **collapses the entire Mac question to Layer 1** — Layers 2 (Python) and 3 (C#/Node) are already cross-platform, so this is "port *one* layer," not "port Rook."
- **The capabilities you most want to keep are the *portable* ones.** Geometry analysis, block merging/analysis, scenegraph traversal, the display conduit, and the HTTP server rest on **openNURBS + the Rhino C++ SDK + cpp-httplib**, which exist on Mac. The Windows-only periphery is what needs reimplementation: WMF video → AVFoundation/VideoToolbox; Win32 input hooks → Cocoa/NSEvent; the modal-loop / `CMainThreadDispatcher` → Mac run-loop / GCD; MSVC → Xcode/CMake. It is a **port, not a rewrite.**
- **The real cost is not the one-time port — it is committing to permanent dual-platform native C++ maintenance.** Every future RookNative capability is then built and tested twice. *That* tax — not technical cleverness — is the actual go/no-go.
- **The genuine unknown to verify (do not assume):** how complete Rhino's **Mac C++ SDK** is for the *specific* capabilities relied on (e.g. `CRhinoDisplayConduit`, the analysis / SubD / brep calls). That determines whether the port is "months of mechanical work" or "months plus fighting SDK holes." **Action:** verify against McNeel's Mac C++ SDK docs / dev forum before any commitment.

**Status:** PX-class; a separate go/no-go. **Not** bundled with the MVP (Part VIII) or P1–P7.

### Cross-cutting — **upstream-leverage posture** (how much we mutate Hermes / McNeel)

The benefit of adopting external substrates **rides on *not* mutating their cores** — mutation forfeits exactly the leverage you switched for. The two substrates have *opposite* extension postures:

- **Hermes — aim for ~0 core mutation, and it is designed for that.** Their hard rule: *"plugins MUST NOT modify core files… expand the generic plugin surface, never special-case in core"*; capability lives at the edges (plugins / skills / MCP). So Rook rides Hermes via plugins (KG as a context-engine/memory plugin, tools as a toolset/MCP server, the swarm via native `delegate_task` + providers). **The one mutation risk is the *embed* mechanic** (importing `AIAgent` as a library couples to internals) → prefer the plugin path. If ever tempted to fork Hermes core, **upstream a generic hook instead.** This leverage is strong and sustainable.
- **McNeel — ideally fork *nothing*; adopt the *design*, not the code.** Their plugin is **compile-time/reflection** with no runtime plugin interface; and RookNative is your in-Rhino surface anyway, so what you want is their *router pattern*. Forking the C# router (Q1-B) means re-pointing it at RookNative (Q6) — a **core change → divergence.** And the router-fork's main payoff (Mac) is gated by Layer 1 regardless (Q8). So McNeel leverage = **adopt proven patterns** (`SlotStore` SQLite/WAL/"row-is-the-lock", adopt-reap, crash envelopes, MCPB) + **contribute primitives *up*** (the one healthy mutation direction) + the vendor relationship — **not** "ride their code for free."

**Net asymmetry:** the Hermes leverage is the stronger, more sustainable of the two; lean harder on staying plugin-clean with Hermes, and treat McNeel as "adopt the blueprint, contribute back, avoid the router fork unless something decisive justifies it."

# PART VIII — THE MINIMUM VIABLE PROOF (MVP)

**Goal.** Prove the single load-bearing claim of this architecture — *Hermes can be Rook's Layer-2 runtime, driving the existing C++ floor to do real Rhino + Grasshopper work, as a plugin (no Hermes-core mutation), triggered by a macro brain* — end-to-end, in days, **committing to nothing structural.**

**Concrete target.** From **Claude Code**, request *"make a sphere in Rhino and create a Grasshopper component"* → **Hermes** (the runtime) executes both against a running Rhino → a sphere and a GH component appear.

## 8.1 Fork, or fresh? — the artifact

- **Not a RhinoMCP fork.** McNeel's repo is Layer 3 (router / slots / multi-instance lifecycle). The MVP talks to *one already-running Rhino* and needs none of it.
- **Not a fresh from-scratch repo.** RookNative (the C++ floor) and `bridge.py` already create spheres and GH components today; rebuilding them is waste.
- **The single new artifact is a Hermes *plugin*** — `rook-rhino`, in its own directory/repo (`~/.hermes/plugins/rook/`), per Hermes's hard rule that capability arrives at the edges, never by mutating core (Part V, upstream-posture). **This plugin is the seed of Rook 2.0's Layer 2** — the KG / intent / Chirp moat attaches to it *later* as further plugins / a context-engine, not now.

## 8.2 Wiring

```
Claude Code ──(MCP/ACP)──▶ Hermes ──[rook-rhino plugin: 2 tools]──▶ bridge.call_rhino ──HTTP──▶ RookNative ──▶ Rhino + GH
 macro brain                THE CORE        net-new (~50 lines)            reuse              reuse        reuse
```

## 8.3 Reuse vs. net-new

## 8.4 The plugin (sketch)

```python
# ~/.hermes/plugins/rook/__init__.py   (illustrative — confirm endpoint paths against current server.py)
from rook.bridge import call_rhino            # reuse Rook's existing bridge + discovery

SPHERE_SCHEMA = {"name": "rhino_create_sphere",
                 "description": "Create a sphere in the active Rhino document.",
                 "parameters": {"type": "object",
                   "properties": {"center": {"type": "array", "items": {"type": "number"}},
                                  "radius": {"type": "number"}},
                   "required": ["center", "radius"]}}

GH_SCHEMA = {"name": "rhino_create_gh_component",
             "description": "Create a Grasshopper component on the canvas.",
             "parameters": {"type": "object",
               "properties": {"component": {"type": "string"}, "params": {"type": "object"}},
               "required": ["component"]}}

def register(ctx):
    ctx.register_tool(name="rhino_create_sphere", schema=SPHERE_SCHEMA,
        handler=lambda a, **k: call_rhino("/geometry/sphere",
                                          {"center": a["center"], "radius": a["radius"]}))
    ctx.register_tool(name="rhino_create_gh_component", schema=GH_SCHEMA,
        handler=lambda a, **k: call_rhino("/gh/component", a))
```

The handlers hit the **same RookNative endpoints `server.py` already calls** — the C++ floor does the real work, unchanged.

## 8.5 The proof — four checkpointed steps

| Step | Action | Checkpoint (pass ⇒ proceed) |
|---|---|---|
| **0 — smoke (zero code)** | Rhino + RookNative running. `curl` the sphere endpoint directly, *or* point Hermes at Rook's *existing* MCP server and ask for a sphere. | Sphere appears / endpoint responds. **Connectivity proven before any build.** |
| **1 — sphere via Hermes** | Write the plugin's sphere tool; register it. `hermes "create a sphere radius 5 at the origin"`. | Sphere appears in Rhino, created by **Hermes**. *(Hermes is now at the core.)* |
| **2 — GH component** | Add the GH tool. `hermes "add a Grasshopper component"`. *(Prereq: Rook's C# companion loaded — true today.)* | Component appears on the GH canvas. |
| **3 — Claude Code trigger** | Connect Claude Code → Hermes (Hermes ships an MCP/ACP server surface). From Claude Code: *"make a sphere and a Grasshopper component."* | Both happen. **Full top→bottom flow** (macro brain → worker engine → floor) proven. |

## 8.6 What it proves — and what it defers

**Proves:** Hermes as Layer-2 runtime, over the existing C++ floor, as a plugin (zero Hermes-core mutation), end-to-end from the macro brain. The whole Layer-2-on-Hermes bet, working, in days.

**Deferred on purpose:**
- **KG / intent subsidy** (the moat) — added later as a Hermes context-engine / memory plugin onto this same skeleton. The MVP uses dumb direct tools deliberately.
- **Layer 3 / McNeel router** — multi-instance lifecycle; not needed for one Rhino.
- **Local models** — use Claude as the MVP worker; swapping to Ollama is a `model_profiles` / providers *config* change, not a rebuild.
- **Fan-in / multi-file** — north-star P6–P7.

## 8.7 First risk retired, and honest unknowns

**Retires the gating risk:** *can Hermes cleanly be the runtime over the existing native floor, via the plugin surface, without forking it?* A "no" (Hermes's process model vs. Rook's discovery; or an insufficient plugin surface) surfaces on **day one**, cheaply, before any structural commitment.

**Unknowns to pin during the build:**
1. **Step 3's Claude Code ↔ Hermes wiring** (ACP vs MCP) — the one path not yet seen end-to-end. Steps 0–2 do not depend on it, so the core is proven even if Step 3 needs iteration.
2. **Reuse vs. reimplement the bridge** — `import rook.bridge` is fastest but couples the plugin to Rook's Python package; a ~20-line standalone discovery + POST keeps it clean. Small, reversible call.
3. **Exact RookNative endpoint contracts** for sphere + GH — confirm against the current `server.py` tool implementations during Step 1–2.

## Decision log

- **The architecture is a three-layer spine** (in-Rhino floor / Python brain / access layer), each with one home language. This is the cure for the C++/C# rubberbanding (Part II).
- **The bridge language is not the architecture**; the layering is. (Part III, Layer 2, finding 2: the inner vs. outer boundary distinction.)
- **Layer 1 (RookNative/C++) stays** but shrinks to its genuine native core (~5% truly C#-impossible; the rest is control/consolidation/commodity). (Part III, Layer 1.)
- **Layer 2 (the brain) stays Python permanently** and is the product; it is already transport-agnostic and ~40% toward local-model coordination. (Part III, Layer 2.)
- **Layer 3 leverages McNeel** (Rhino-agnostic router; no invariant collision). Its home language is the lead open question, likely decided by cross-platform. (Part III, Layer 3; Part V, Open Q1.)
- **The C#→C++ history was about a bad in-house C# bridge, not C# itself** — so re-introducing C# at the *out-of-Rhino* Layer 3 does not reopen the original UI-thread/GH wounds. (Part III, Chesterton's fence.)
- **Vision is the anchor; implementation and path are refinable.** (How to read this document.)
- **Layer 2 has an internal leverage/moat split:** an agent-runtime substrate (candidate: **Hermes**) + the domain intelligence (KG/intent/Chirp). Hermes belongs at the **bottom (worker) tier**; **Rook owns the top coordinator and the product identity** — *not* Hermes as the outer host. Adoption topology is Open Q7.
- **The empirical bet has partial prior evidence (Engram):** B≈A confirmed; C≫D conditional and modest; **context economy** is the real variable; **finetuning-as-shortcut** is a flagged risk. The Rhino probe is the domain-specific test (Open Q3).
- **The MVP / first concrete step is a Hermes plugin** (`rook-rhino`) over the existing RookNative floor — **not** a RhinoMCP fork, **not** a rebuild. A four-step proof (curl → Hermes sphere → Hermes GH → Claude Code) retires the gating risk in days (Part VIII).
- **Cross-platform / Mac:** the only non-degrading path to native Mac is **porting Layer 1 (C++) to macOS**; Hermes does not solve Mac; the value (geometry/scenegraph/block-analysis) is the *portable* part; the cost is **permanent dual-platform native maintenance**; the workaround (Windows-in-the-loop) is rejected as "the architecture" (Open Q8).
- **Upstream-leverage posture:** Hermes — **~0 core mutation, by design** (ride upstream via plugins). McNeel — **adopt patterns + contribute primitives up, avoid the router fork.** Mutating either core forfeits the leverage that justified switching (Part V).
- **Do not over-read the "~5%."** It means "no managed API exists," not a benchmark; the native-vs-managed line is set by **profiling hot paths**, and the C++ core is kept where it earns its keep (Part III; Open Q8).
