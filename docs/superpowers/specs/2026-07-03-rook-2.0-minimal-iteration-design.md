## 1. The thesis (why 2.0, and why now)

Stated by Aaron 2026-07-03:

> Hermes is the future. Everyone will have agents, open-weight models will be predominant, hardware will run local models, brownfield software will survive only if it has agentic plugins for your agent.

The consequence for Rook: **the harness belongs to the user, not to the product.** Rook stops being an application that hosts an agent and becomes **the brain that makes any agent competent in Rhino** — knowledge, contracts, typed tools, verification discipline — delivered *to* the user's agent as a plugin.

Two poles now exist in running code, and they bet opposite ways:

| Pole | Bet | Evidence (code) |
|---|---|---|
| **McNeel pole** (Rook-2 fork) | The app hosts the agent: in-Rhino AI Panel, Claude-first onboarding ("auto-detect `claude`, just GO") | `rhino/plugin/UI` AI Panel; `PLAN.md` decisions table; `connector/` = Claude Desktop MCPB; `cc-plugin/` = Claude Code agents+skills |
| **Hermes pole** | The user owns the agent: open-source, model-agnostic, local-model-first harness; apps arrive as plugins | `hermes_cli/plugins.py` plugin system; `plugins/` ecosystem; native Windows install; 462 contributors in 3 weeks |

**Rook 2.0's position: the pole-independent brain, wired to both poles through the two protocols they already speak — MCP for tools, ACP for agents.** Neither pole has Rook's core: McNeel's grounding is pull-only `get_context` and its safety model is auto-grant-all + per-turn undo (`PLAN.md`); Hermes has no Rhino knowledge and no typed-contract discipline. Both need what Rook builds.

Hermes is the primary integration target for this iteration (the strongest open, real agentic framework today). Claude Code and Codex get the same contracts later through the same seams (Phase 3) — the architecture is harness-agnostic; Hermes is the flagship.

## 2. Decisions locked in the design session

1. **Hermes-primary, Claude/Codex-secondary.** Focus the minimal iteration on Hermes; Claude/Codex parity arrives via the same MCP/contract surfaces, not separate builds.
2. **The fork (Rook-2) is the McNeel-pole adapter and de-Clauding lab — not a rebase substrate.** Rook's brain is not re-homed onto it. Its minimal-iteration role is the ACP panel seam plus GH2 early warning.
3. **Rook core campaigns are untouched.** LM (worker reliability) and PH (planner harness) proceed exactly as planned; `workflow_validate`/`workflow_run` remain the gate for the differentiated contract export (Phase 3).
4. **Hermes coupling is ABC-and-config only.** Pin a Hermes release; touch only documented surfaces (plugin manifest/`register(ctx)`, `mcp_servers` config, `hermes-acp` entry point). Never import Hermes internals. (Hermes moves at ~134 commits/day; 12%+ of commits are agent-authored.)
5. **RookVision placement is open for rethink** (resolved in §6).
6. **No new harness-shell code in Rook.** Gateways, cron, session recall, skills-management — never built; they are what the Hermes pole provides.

## 3. What "minimal and functional" means

**Success definition.** On a machine with Rhino + Rook installed, a user can within one hour:

1. Install Hermes (native Windows installer).
2. Run one Rook-provided setup command.
3. Drive Rhino and Grasshopper from *their own agent* — cloud brain or local model — with Rook's knowledge discipline active (query-before-compose, batch canvas path, correction recording).
4. Optionally see that same agent operating *inside Rhino* via the fork's AI Panel.

That is the two-pole thesis in running code. Everything else is deferred.

## 5. The seams — grounded in code

Every load-bearing claim below was verified in the three working trees on 2026-07-03.

### 5.1 Hermes ⇄ Rook tools: MCP stdio + the lean profile (zero new transport)

- Hermes has a native MCP client with `mcp_servers.<name>` config (stdio `command`/`args` or HTTP), include/exclude tool filtering, and live `list_changed` handling (`tools/mcp_tool.py:1524ff`).
- Rook's MCP server is stdio (`python -m rook`) and ships the tool-exposure profiles from PR #382: `ROOK_MCP_TOOL_PROFILE=lean` advertises **22 tools** (`mcp_tool_profiles.py:48` `PUBLIC_LEAN_TOOL_NAMES`): ping/instances/session management, `knowledge_query`/`rhino_knowledge_query`/`gh_knowledge_query`, `rhino_objects`/`rhino_geometry`, `gh_snapshot`/`gh_edit`/`gh_errors`, the two `execute_intent` routes, and the four `rook_tools_*` meta-tools.
- **The June-thread limitation is already solved server-side.** The 2026-06-11 rhizome investigation flagged Hermes's include-list as a static budget with "no progressive disclosure." The capability-index campaign (PR #388) shipped `rook_tools_ls/search/read/call` — progressive disclosure *behind* a small advertised surface. A local model gets 22 schemas in context and can still reach all ~430 tools on demand through `rook_tools_call`. This pairing (lean + PD meta-tools) is the designed diet for weak local brains and needs zero new code.

### 5.2 The `rook` Hermes plugin: discipline, not transport

- Hermes plugins are directories with `plugin.yaml` + `register(ctx)`, loadable from `~/.hermes/plugins/`, a project dir, or a **pip entry point** (`hermes_agent.plugins` group) (`hermes_cli/plugins.py:1–35`). Their policy: third-party product plugins ship standalone, never into Hermes core (`build-a-hermes-plugin.md`) — exactly the ~0-core-mutation posture the anchor prescribed.
- `PluginContext` provides: `register_tool` (into toolsets), slash/CLI commands, **bundled skills**, ~25 lifecycle hooks incl. `post_tool_call`/`transform_tool_result`, and `ctx.llm` structured calls (`plugins.py:337ff`).
- **The plugin does not own transport.** Rook tools flow through Hermes's native MCP client (§5.1). The plugin adds the three things raw MCP cannot: setup automation, the knowledge discipline, and the correction loop (§7, Phase 1 scope).

### 5.3 Hermes ⇄ fork panel: ACP, both ends already speak it

- The fork's single internal agent contract is **ACP** (`PLAN.md`: "ACP is the one internal contract"). Its `AgentRegistry` seeds built-ins (claude, codex, gemini) and **overlays custom `AgentDefinition` entries from settings** — a custom entry with a new name is appended; the record carries `name, adapter, command, searchPaths, model, args, enabled` (`rhino/plugin/Agents/AgentRegistry.cs`).
- The Gemini path is a **native ACP stdio client**: `AgentFactory` → `GeminiConnection.Connect` spawns `<command> --experimental-acp` and drives it with the fork's own `ClientSideConnection` (`rhino/acp/` library) (`AgentFactory.cs:12`, `GeminiConnection.cs:28`).
- Hermes ships a full **ACP stdio agent server**: `hermes acp` subcommand and `hermes-acp` console script (`pyproject.toml:310`), stdout reserved for ACP JSON-RPC (`acp_adapter/entry.py`), rich capabilities including session forking, model selection, and `McpServerStdio/Http` passthrough (`acp_adapter/server.py`).
- **Therefore the bridge is one custom `AgentDefinition` away**, with one known friction: the hardcoded `--experimental-acp` argument. Two mitigations, in order of preference: (a) a `hermes-acp.cmd` wrapper that swallows unknown args — zero fork changes; (b) a ~2-file fork generalization: rename/extend `GeminiConnection` into an `AcpConnection` that honors `def.Args` instead of the hardcoded flag — small, clean, and an obvious **upstream PR candidate** (it makes *their* product generically ACP-capable, which their own architecture already implies). Version note: Hermes pins `agent-client-protocol==0.9.0`; the fork's `rhino/acp` is codegen from the same schema family — the Phase 2 spike validates compatibility before any build.

### 5.4 What the minimal iteration deliberately does NOT take from the fork

- **Not the router** (stdio→HTTP proxy): it targets *their* in-Rhino listener and tool set, not RookNative; re-pointing it is the anchor's Open Q6 cost and buys nothing at single-instance scale.
- **Not their in-Rhino tool core** (~20 thin-waist tools: `get_context`, `run_python/csharp`, doc/selection/view ops — `rhino/plugin/Tools/`). Their philosophy is code-as-tool-use escape hatches; Rook's is typed routes + knowledge. RookNative remains Rook's sole in-Rhino surface (anchor invariant 2 stands).
- **Watch, don't adopt: GH1/GH2 tool dirs.** The fork is the early-warning system for GH2/Rhino 9 tool shapes (their headline bet). Rook's GH knowledge corpus is GH1; a GH2 knowledge track is a future campaign, not this iteration.

## 6. RookVision placement (the rethink)

**Current state (corrected):** RookVision is not browser-served today — it is an in-Rhino Eto WebView panel (`src/Rook/UI/Vision/RookVisionPanel.cs`, `VisionWebSurface.cs`) over the shared `RookWebSurface` web-hosting layer, with presentation diagnostics (`rhino_vision_presentation`). The browser era was Rook 1.0-early.

**Options considered:**

- **(a) Status quo** — in-Rhino WebView panel via the C# companion. Zero work. Requires the companion, which ships anyway (GH callbacks live there).
- **(b) Move to the fork's panel substrate** — RookVision as a tab beside the fork's AI Panel. Attractive convergence, but it couples Rook's approval UX to fork divergence *now*, for zero new capability.
- **(c) Move to Hermes surfaces** (dashboard/web UI) — puts the approval gate in the agent's UI. **Rejected on principle:** the approve/consume gate is a *human* safety boundary bound to the Rhino document (approved media flows into the model); it must live Rhino-adjacent and Rook-owned, and must never sit inside the surface the agent controls. (Consistent with `tool_groups.py` keeping vision groups MCP-only, away from internal agents.)

**Decision: (a) for the minimal iteration, with the "one web app, many mounts" rule made explicit for later.** RookVision stays the Rook-served web app it already is; its mounts evolve — in-Rhino WebView today, a fork-panel tab as a Phase 4 convergence, browser as the headless fallback. Hermes never mounts it; Hermes gets *tools* (`rhino_vision_artifacts`, `rhino_vision_consume_approved`) and, if useful, a tool returning the gallery's local URL. The invariant to carry forward: **generation may someday offload to Hermes providers (the ~9.3k-LOC fal layer in `Services/Vision/Video/` is the best offload candidate found), but the artifact registry and the approval gate stay Rook-owned unconditionally.**

## 7. The roadmap — phased, grounded, checkpointed

Phases are dependency-ordered. Each has acceptance criteria that are observable, not aspirational. Phases 0–2 are the minimal functional iteration; 3–4 are the committed direction behind their gates.

### Phase 0 — Connectivity smoke — ✅ ALREADY VALIDATED (Aaron, pre-spec)

**Status update (2026-07-04 review):** Aaron has already run this configuration — `hermes mcp add rook` against the stdio MCP server with the lean profile — **with many free open-weight models**. The connectivity, tool-wall, and foreign-harness risks this phase existed to retire are retired, and more thoroughly than the spec asked (a model panel, not a single smoke).

Remaining Phase-0 work is bookkeeping, not validation:

- **Record the evidence baseline:** which models were tested, which completed which operations (ping / snapshot / edit / intent), and where they struggled. This becomes the spec's model-panel baseline and directly informs Phase 1's local-brain acceptance measurements (and is prior art the LM campaign should see).
- **Pin the versions** the testing ran against (Hermes release, Rook commit, profile) as the plugin's initial support matrix.
- **Retired:** transport risk, tool-wall risk, PD-through-a-foreign-harness risk. (This was the 2026-06-11 rhizome thread's blocker, resolved with the config it predicted — now empirically, across a panel of open-weight brains.)

### Phase 1 — The `rook` Hermes plugin v0 (~3–5 days) — the core slice

**Home:** in this repo, `integrations/hermes/`, exposing the `hermes_agent.plugins` pip entry point (installable standalone per Hermes policy, versioned with the tools it wraps). **Contents — exactly four things:**

1. **`hermes rook setup`** (plugin CLI command): discover the Rook install (repo path + `%TEMP%/rook/` discovery files), author the `mcp_servers.rook` config entry with the lean profile, verify with a ping. Idempotent.
2. **Bundled skill** — the knowledge discipline as portable text: query `knowledge_query`/`gh_knowledge_query` before composing; prefer `gh_snapshot`→`gh_edit` batch path; `gh_errors` after solve; record corrections. (This is CLAUDE.md-as-code for harnesses that can't read CLAUDE.md — the plugin's real payload.)
3. **Correction-loop hook** — `transform_tool_result`/`post_tool_call`: when a Rook result carries `correction_detected: true`, surface a visible nudge to call `knowledge_record`. **Doctrine: nudge, never auto-write** (mirrors the Hermes-adoption memo's approval-preserving rule).
4. **README + version pin** — supported Hermes release, supported Rook release.

- **Accept when:** on a fresh Hermes install, `hermes rook setup` → a golden canvas task ("create a radius slider wired to a sphere, verify no errors") completes via a Claude brain using the batch path (observable: `gh_edit` with epoch, not per-component calls); the same task attempted with `qwen3:14b` local produces a *measured* result (success or characterized failure — measurement, not a gate; qwen3's LM5 record justifies optimism, not assumption); the seeded-failure correction nudge fires; nothing writes to knowledge stores without explicit action.
- **Retires:** "plugin surface fits Rook" risk; produces the first live data on a non-Claude harness driving Rook with discipline.

### Phase 2 — Fork ACP seam: the user's agent inside Rhino (spike + ~2–4 days)

- **Spike first (timeboxed 1 day):** custom `AgentDefinition {name: "hermes", adapter: Gemini, command: <hermes-acp wrapper>}` + wrapper `.cmd` swallowing `--experimental-acp`. Validates ACP schema compatibility (their codegen vs `agent-client-protocol==0.9.0`) before any fork edit. If the wrapper path fails on args or schema, fall to the ~2-file `AcpConnection` generalization (honor `def.Args`); prepare it as an upstream PR either way.
- **Accept when:** the fork's AI Panel lists "hermes" as an available agent; a panel conversation drives Rook tools (Hermes's MCP config from Phase 1 carries over — the panel-hosted Hermes loads the same `mcp_servers.rook`); transcript renders in panel bubbles; a local-model brain works in-panel (the fork's Claude-focus is now demonstrably a default, not a limit).
- **Divergence budget:** ≤2 files + settings docs. Anything larger stops and gets re-scoped.
- **Retires:** the two-pole fusion risk — after this, "your agent, in the vendor's panel, with Rook's brain" is a screenshot, not a slide.

### Phase 3 — Contracts export (GATED on the PH track shipping `workflow_validate`, then `workflow_run`)

- Plugin update: expose `workflow_validate`/`workflow_run` + a payload-authoring skill. Hermes becomes the second external convergence proof (after Claude Code) on the same compiler, per the north star's no-fork rule.
- **Claude/Codex parity lands here:** a `cc-plugin`-shaped package (the fork's own `cc-plugin/` is the template: agents + commands + skills) exposing the same contracts to Claude Code; Codex via MCP config. Same payloads, same compiler — parity is packaging, not new architecture.
- **Accept when:** a Hermes-authored payload validates and executes with typed receipts; an intentionally-invalid payload is rejected by the compiler with the same diagnostics the internal planner gets.

### Phase 4 — Post-minimal convergences (each its own future slice; listed to mark direction, not commitment)

- RookVision fork-panel mount (§6's second mount).
- Vendor-provider offload: image/video generation via Hermes provider plugins when Hermes-in-the-loop (the `fal` overlap); approval gate stays Rook-side.
- Hermes kanban as a coarse-job farm (whole Rhino tasks, never contract-gated node resolution — the LM5 worker box is not an agent loop, by design).
- KG-as-MemoryProvider experiment (the Open-Q3 rig, now with a documented ABC).

### Standing obligations (all phases)

- LM/PH campaigns proceed untouched; this iteration must never block or fork them.
- Weekly `git fetch` on the fork against `mcneel/RhinoMCP` upstream; divergence reviewed, upstream PRs preferred.
- Hermes pinned by release; coupling audited against the documented surfaces only.

**Version discipline (LM5K manifest practice, generalized):** every phase evidence run records the 4-tuple — Rook commit × plugin tag × Hermes version × Rook-2 branch/commit. The plugin README's support matrix is the running record.

**Why the plugin is out-of-tree (the resolution of OQ1):** (a) the thesis makes it the public artifact — installable by anyone via `git clone`/pip without touching Rook core's visibility; (b) Hermes's ~134-commit/day velocity is absorbed by plugin point-releases instead of Rook releases; (c) the coordination surface back to Rook is thin (a tool-name list + a skill file) and cheap to drift-check; (d) it keeps the "separation" problem from existing at all inside Rook — there is nothing to separate because the only new code lives elsewhere.

**Signposted, not created:** a fourth distribution/packaging repo (installer composing plugin + fork build + profiles) belongs to Phase 4+, not now.

## Decision log

- Rook 2.0 = the pole-independent brain; MCP is the tool wire, ACP is the agent wire; Hermes-primary, Claude/Codex via the same contracts.
- The minimal iteration is composition, not construction: ~300–500 new plugin lines + ≤2 fork files; Rook core unchanged.
- The lean profile + `rook_tools_*` progressive disclosure is the designed surface for foreign/local-model harnesses (the June tool-wall finding, answered by the capability-index campaign).
- The plugin's payload is discipline (skill + correction nudges + setup), never transport, never auto-writes.
- RookVision: Rook-served web app, in-Rhino mount today, fork-panel mount later, never mounted in the agent's own UI; approval gate Rook-owned unconditionally.
- The fork is leverage for ACP/panel/GH2-watch; router and tool core stay unadopted; divergence is budgeted and upstream-pointed.
- LM/PH campaigns are the moat's production line and proceed untouched; `workflow_validate`/`workflow_run` gate the contract export (Phase 3).
- Repo topology (§11): three repos + one tracked upstream — Rook = brain (existing discipline, no new scheme), `rook-hermes-plugin` = the only net-new code home (standalone, public), Rook-2 = ff-mirror main + budgeted feature branches (adapter lab, not a base), Hermes = pinned releases, never forked.
- Every evidence run records the version 4-tuple: Rook commit × plugin tag × Hermes version × Rook-2 commit.
